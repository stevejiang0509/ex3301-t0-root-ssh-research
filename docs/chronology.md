# 从原厂管理界面到 root SSH：已验证时间线

本记录仅描述一台所有者授权测试的 Zyxel EX3301-T0。原始报告留在私人工作区；本仓库不含登录凭据、设备标识、配置备份或固件文件。

| 阶段 | 观察与操作 | 验证边界 |
| --- | --- | --- |
| 1. 找回管理入口 | 电脑以网线直连设备，按本机网络信息确认管理地址，登录 Hyperoptic `V5.50(ABVY.4.1)Y1` 后台。 | 最初猜测的地址并非实际管理地址；这一步没有提升权限。 |
| 2. 显示固件升级页 | 当时登录账户为 `medium` 管理员。向 `login_privilege` 中该角色的 `Page` 加入 `Firmware_Upgrade`；服务端新读取的 `MenuList` 出现升级入口，其他已采集权限项保持原值。 | 只验证了页面可见，不代表获得 Linux root，也不代表任意固件会通过校验。 |
| 3. 限制 SSH 范围 | 将 SSH 管理服务设为 `LAN_ONLY`，读取配置确认生效。管理员密码可登录 SSH，但提示符为 `ZySH>`，当时没有 Linux shell。 | 此时 `modelcheck` 和 `fwidcheck` 查询均显示启用；SSH 可登录不等于 root。 |
| 4. 切换官方固件 | 首次从 Y1 上传官方 C0 包时，页面报“Image uploading failed”；具体后端子校验未查明。随后在 Y1 中关闭 `modelcheck` 与 `fwidcheck`，上传官方 `V5.50(ABVY.7.2)C0`。重启后后台显示该版本，原管理员可登录，SSH 仍为局域网访问。 | 记录证明了这台设备上的操作顺序和最终结果；没有独立实验能证明仅关闭两项检查就足以刷入。`modelcheck`、`fwidcheck` 与 7.2C0 的 RSA 镜像签名检查是不同机制。 |
| 5. 发现日志配置注入 | 对 7.2C0 解包后的 DAL、后端库和 syslog-ng 组件作静态分析。经认证的 `logset` 写入将 `LogServer` 拼入 syslog-ng 配置；特定配置语法可引入 `program()` 源。 | 根因是配置文本注入，不是 SSH 登录接口本身的漏洞，也不是直接把字段传给 shell。静态分析单独不能证明设备上执行。 |
| 6. 动态证明 root 执行 | 在现有管理员会话下短暂提交测试用日志设置，在独立的局域网 SSH PTY 中观察到 `uid=0(root) gid=0(root)`。随后按顺序清除注入字段、恢复原日志模式，并重新读取全部原始字段核对。 | 这证明设备上的日志服务以 root 执行了测试命令。测试脚本自己的状态文件没有捕获 UID；UID 由 SSH 观察记录单独证明。未刷写固件或更改启动槽。 |
| 7. 获得 root SSH | 用已验证的临时 root 通道，先在 RAM 中准备账户文件副本，再仅将运行时 `admin` 的 UID/GID 从 `21/21` 改为 `0/0`、登录 shell 从 `/usr/bin/zysh` 改为 `/bin/sh`。新建 SSH 会话登录成功，独立执行 `id -u` 返回 `0`；密码字段和其他账户保持原值。 | 只在当次启动的运行时账户文件上验证。没有安装持久化启动钩子；重启或原厂账户重建可能还原。 |
| 8. root 账号单独验证 | 之后用系统自带 `passwd` 更新运行时 root 凭据，并用新的 SSH 会话验证 `uid=0(root)`。 | 未验证凭据在重启后保留；此操作不是发现漏洞的必要条件。 |

这里的“最高权限”指 Linux `uid=0`。记录没有证明所有 Y1 设备、其他 C0 小版本或后续系统都存在相同行为。
